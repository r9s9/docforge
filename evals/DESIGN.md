## 0. Ground rules

1. **The app is never changed.**
   - Nothing under `backend/` or `frontend/` is edited, and master stays as it is.
   - Eval work lives on the `evals` branch, as new files under `evals/`, `tests/evals/`, `docs/`
     and `.github/workflows/evals.yml`, plus `CLAUDE.md`.
   - The one planned edit to an existing file is the README section in M5, and it stays on `evals`.
2. **Test the real thing.**
   - Runners call DocForge's real service functions. Pipeline logic is never copied into eval
     code.
   - Where the evals need to see inside a run (the HTTP cache, the judge's verdicts, AI call
     outcomes), they wrap a function in memory, inside the eval process. No source file changes.
3. **Synthetic data only.** Every document is generated by the corpus builder or made by hand by
   the project owner. People and companies are invented (§4.6).
4. **Money.** Every AI run has a cap (`--max-usd`, default $3). A run that would cost more needs
   the owner's go-ahead first.
5. **Secrets.** Keys come only from environment variables. They are never printed, logged or
   written to a result file or the cache.
6. **No invented numbers.** `RESULTS.md` is only written by `python -m evals report`. If a metric
   looks wrong, the cause gets investigated and written down. The number is never adjusted.
7. **Evals never touch the hosted app.** Runs go to model APIs with the owner's key, never to
   app.docforge.live or its free tier.

### 1.2 Where the code differs from the brief

| # | Brief | Code | Consequence for the evals |
|---|---|---|---|
| 1 | The judge "adds to the deterministic score but never overrides it". | `judge_compliance` appends a `semantic` dimension and never changes `report.score` or `report.grade`. | The headline score and grade are the same with and without AI. Score separation is reported on `score` in every mode, and on the semantic score in AI modes. |
| 2 | The judge labels each difference material or benign. | The `material` verdict (`LLMComplianceVerdict`) is not stored. The judge rewrites `severity`, appends its rationale to `message`, and counts the material differences for the semantic dimension. | The eval process records the verdicts as they're returned (§6.4). |
| 3 | — | Content that appears only in the checked document lands in `alignment` with status `extra`. It never becomes a difference, never affects the score and is never sent to the judge. | An inserted clause can only be detected through `alignment` (§5.1). |
| 4 | — | A FIXED element counts as changed only when `SequenceMatcher` similarity drops below 0.9. | A one-number edit inside a long clause may stay above 0.9 and go unreported. The judge only sees reported differences, so it can't catch the edit either. See H1 (§9). |
| 5 | Removing a table column gives `table_shape`. | Alignment (`multi_doc_differ._align`) runs `difflib.SequenceMatcher` over element signatures and pairs elements by position inside "replace" blocks. `align_signature` keys tables on their whole header row, and headings on their lower-cased text. | A table whose header changed can still be paired by position. If the rest of its header is at least 0.8 similar, nothing is reported. If it isn't paired, the result is `missing_table`. | 6 | Analyze modes are "smart detect / full template". | The modes are `mode="smart"` and `mode="tags_only"`. | The evals use the code's names. The suite runs `smart`, the default. `tags_only` is optional. |
| 7 | The fixer "restores changed or missing boilerplate". | `fix_document` patches FIXED *paragraphs* only. Tables and fields are never touched. | 10 | Python 3.11. | `backend/.python-version` and the Dockerfile use 3.12. Ruff targets `py311`. | CI runs on 3.12. The eval code stays 3.11-compatible. |
| 11 | `sampledata.py` has four builders. | Three types are registered in `_BUILDERS`. `build_service_agreement` exists but is not registered. | The corpus has its own builders and reuses the patterns: the labelled paragraph, the filled table, the PAGE field. |
| 12 | — | `Settings` reads `.env` from the working directory. `db/session.py` builds its engine at import time. | 13 | Configs are YAML. | PyYAML is not a direct dependency. It is only installed through `uvicorn[standard]`. | `evals/requirements.txt` adds `pyyaml>=6`. `backend/pyproject.toml` stays untouched. |
| 14 | Generate "fills it from notes". | With AI on, generation runs a writer pass, then a read-back review (`ai_verify_enabled`) that can buy one rewrite. The writer is skipped above 60 fields (`MAX_WRITER_FIELDS`) and falls back to route + compose. | Generate cost and latency include the review and the rewrite. The result file records which passes ran. |
| 15 | — | The Anthropic SDK (1.17.0) sends its requests through `httpx2`, a package separate from the `httpx` that DocForge's OpenAI-compatible path calls. | The response cache wraps both transports (§6.2). |

## 2. Architecture

### 2.1 Layout

```
evals/
  README.md          how to run, how to read results
  DESIGN.md          this file
  CHANGELOG.md       one entry per milestone
  requirements.txt   pyyaml>=6 (the app installs unchanged: pip install -e backend)
  .gitignore         cache/ and corpus/build/
  __main__.py        python -m evals ...
  harness.py         sandbox: environment, database, AI settings
  cache.py           HTTP record/replay
  observe.py         in-memory wrappers: AI call outcomes, judge verdicts, spend
  configs/           no-ai.yaml, haiku.yaml, local.yaml (LM Studio)
  corpus/
    generator.py     deterministic builder engine + ground truth
    doc_types/       one spec per document type, EN/DE text
    mutators.py
    notes/           rough-notes inputs + expected values (M3)
    handmade/        the messy set + labels (committed)
    manifest.json    every case + its labels (committed)
    NAMES.md         invented names and how they were checked
    build/           built .docx files (gitignored; rebuilt by `corpus build`)
  runners/           analyze.py, generate.py, comply.py
  metrics/           pure functions, unit-tested
  graders/           rubric grader for free-text fields (M3)
  cache/             cached model responses (gitignored)
  results/           <date>_<config>_<suite>.json (committed)
  thresholds.yaml    CI gate (M5)
  RESULTS.md         written only by `python -m evals report`
tests/evals/         tests for mutators, metrics, grader, cache, ground truth
  conftest.py        puts the repo root on sys.path
```

**Test layout**
- Tests run from the repo root with `python -m pytest tests/evals -q`. There is no root pytest
  config, so the backend's own pytest setup is unaffected.
- `tests/evals/` has no `__init__.py`. Without one, pytest can't import it as a package named
  `evals` and shadow the real one.
- Metric and mutator tests don't import `docforge`, so they stay fast.
- Tests that run a suite start a subprocess, so each one gets a fresh sandbox.

### 2.2 The sandbox (`evals/harness.py`)

`python -m evals run` prepares one sandbox per run, before anything imports `docforge`:

1. Create a temp directory. Set `DOCFORGE_DATA_DIR` to it and `DOCFORGE_DATABASE_URL` to a SQLite
   file inside it.
2. Set `DOCFORGE_STORAGE_BACKEND=local`, `DOCFORGE_FREE_AI_ENABLED=false`,
   `DOCFORGE_AUTH_REQUIRED=false`, `DOCFORGE_SERVERLESS=false` and `DOCFORGE_LOG_LEVEL=WARNING`.
   In pydantic-settings, environment variables win over `.env`. A developer's `.env` (Supabase
   storage, a free-tier key, a production database URL) therefore can't leak into a run.
3. Import `docforge` and call `docforge.db.session.init_db()`.
4. Apply the config's AI settings (§6.1) to the cached `get_settings()` object, in memory only:
   - provider, base URL, model and reasoning model
   - effort levels, temperature and timeouts
   - `ai_max_parallel_calls`, `ai_writer_enabled` and `ai_verify_enabled`

   The key is read from the environment variable the config names and set as `ai_api_key`.
   `no-ai.yaml` forces `ai_enabled=False` and an empty key.
5. Install the HTTP cache (§6.2) and the call observer (§6.4).

**Every service call passes `owner_id=None`.**
- `ai_quota.plan_ai_for_owner` then returns the global plan, which is our settings.
- Free-tier accounting is skipped.
- The learning loop (`services/learning.corrections_fewshot`) stays empty, so earlier cases
  can't steer later ones.

The temp directory is removed at the end of the run unless `--keep-sandbox` is given.

### 2.3 How each runner calls the services

All runners follow the flow of `backend/tests/integration/test_flows.py`: store → analyze →
publish → generate / check / fix.

**Frozen templates for generate and comply**
- Generate and comply need a published template. For each document type, the run builds one,
  once:
  - store the 5 example documents
  - run `analyze_documents(mode="smart")` with AI **off**
  - run `publish_template`
- Every mode is then measured on the same template. A difference between modes comes from the
  step being measured, not from a different template. Template quality has its own suite
  (analyze).
- The template is rebuilt on every run. The no-AI analyzer is deterministic, so prompts, and
  therefore cache keys, stay stable from run to run.

**Comply, per case**
1. `check_document(db, template, filename=..., data=...)`.
2. Map `report.differences[*].node_id` and `report.alignment[*]` to logical elements (§3.4).
3. Attribute them to the case's injected deviation (§5.1), with the judge's verdicts taken from
   the observer.
4. For fixable cases, run `fix_document(...)`, then `check_document` on its output.

**Generate, per case**
1. `generate_document(db, template, GenerationInput(mode=UNSTRUCTURED_TEXT, raw_text=notes))`.
2. Read from the `GenerationRequest` row:
   - `context_used`: the values that were rendered
   - `routing`: its source, placements with `ai_drafted`, and `render_review`
   - `token_usage`
3. Load the output .docx from storage for the layout check.

**Analyze, per case** (one document type × k examples)
1. Store the first k examples, then run `analyze_documents(mode="smart")` and `publish_template`.
2. Compare `classification.classifications` and `field_definitions` with the ground truth of the
   representative document (`job.representative_document_id`).
3. Compare `template.docx` with the representative for layout.

### 2.4 CLI

```bash
python -m evals corpus build                                  # build the corpus, write manifest.json
python -m evals run --suite comply --config configs/no-ai.yaml
python -m evals run --suite all --config configs/haiku.yaml --max-usd 3
python -m evals report                                        # rebuild RESULTS.md from results/
python -m evals compare results/A.json results/B.json        # what got better or worse
```

Extra flags for `run`:
- `--types`: a subset of document types
- `--limit N`: the first N cases per type, for smoke runs
- `--no-cache`: always call the model (§6.2)
- `--repeat K --sample N`: stability runs (§5.4)
- `--dry-run`: print the case list and the cost estimate, then stop without calling anything
- `--keep-sandbox`: keep the temp directory for debugging

## 3. Ground truth and DocForge's IDs

### 3.1 How DocForge numbers elements

`structure_normalizer.walk_document` gives every paragraph and table a `node_id` in walk order:
`n0001`, `n0002`, and so on.

- **Body first.** A table is followed right away by its cells' paragraphs, row by row, skipping
  repeats from merged cells.
- **Then headers and footers.** These come per section, skipping sections whose header or footer
  is linked to the previous one.
- **Shared walk.** The extractor, the template builder and the fixer all use this walk.

IDs are positional, so they only mean something within one document.

### 3.2 Logical elements

Next to every document it builds, the corpus generator writes ground truth: one entry per logical
element.

```yaml
- id: clause.liability               # stable across every document of the type
  kind: fixed                        # fixed | field | table | auto
  locator: {scope: body, block: 14}  # or {scope: "footer:0", block: 0}
  text: "Except in cases of intent or gross negligence, the total liability of the Supplier
         under this Agreement shall not exceed EUR 250,000 per contract year."
  material_if_changed: true          # feeds the mutator labels and the judge's ground truth
- id: field.date
  kind: field
  field_type: date                   # text | multiline_text | date | money | person
  label: Date
  value: 16 January 2026
  text: "Date: 16 January 2026"
  locator: {scope: body, block: 2}
```

- **Tables** also record their header row, their data rows, and whether removing a row is
  material.
- **Labelled fields** such as "Invoice Date: 23.11.2026" record the label and the value
  separately, matching DocForge's `static_prefix`.

### 3.3 Resolving locators to node IDs

At run time, a locator is resolved against the document DocForge actually sees:
1. Walk the .docx with `walk_document`.
2. Pick the node at that scope and block, plus row and column for cells.
3. Check that the node's text equals the ground-truth text after whitespace normalisation.

If the texts differ, the case fails with an error that shows both texts. A mismatch means the
generator or the walk changed, and the evals never guess.

A unit test builds one document of each type, resolves every locator, and cross-checks the result
against DocForge's own extraction (`structure_normalizer.build_extraction`).

### 3.4 From a template back to ground truth

- **Representative.** A template's classifications and stored extraction use the node IDs of one
  example document, `job.representative_document_id`. The runner keeps a map from stored
  `SourceDocument.id` to corpus document. From it, the runner loads that example's ground truth
  and builds a `node_id ↔ logical id` map.
- **Classifications.** `ElementClassification.node_id` → logical element (analyze).
- **Fields.** `FieldDefinition.node_ids` → logical elements.
  - A field is identified by what it covers, not by its name: field names come from labels, and
    an AI analyzer may name them differently.
  - Table columns are matched by header text (`TableColumn.label`) and by position.
- **Differences.** `ComplianceDifference.node_id` is a representative node ID. It maps to a
  logical element, which is compared with the case's injected deviation.
- **Alignment.** `ComplianceAlignedPair.node_id` is a representative node ID. The exception is
  `extra` rows, which carry the checked document's node ID; those are matched by text.

### 3.5 Generate: expected values

- **What a notes case lists.** Expected values by logical field ID, for example
  `field.invoice_date: "23.11.2026"`.
  - `null` means the notes don't contain the value.
  - An `accept` list allows more than one right answer, for example after a correction in the
    notes.
- **Normalisation.** Values are compared after normalising whitespace and Unicode quotes, and per
  field type:
  - dates: `23.11.2026` = `2026-11-23` = `23 November 2026`
  - money: `1.234,56 €` = `EUR 1,234.56`

  The normalisers are metric code, with unit tests.
- **Form.** Whether the value kept the template's written form (a German date in a German
  document) is a separate metric (§5.2).

## 4. Corpus

### 4.1 Generator and determinism

- **Engine.** `corpus/generator.py`. A document-type spec in `corpus/doc_types/` declares the
  blocks (title, labelled field, clause, heading, table, page-number footer) and their EN and DE
  text. The engine turns a spec plus a value set into a .docx and its ground truth.
- **Values.** Value sets come from seeded generators (`values.seeded(pair, key, index)`, i.e.
  `random.Random("<pair>:<key>:<index>")`). String seeds are hashed with SHA-512, so they're
  stable across runs and machines. There is no clock: dates are drawn from fixed ranges. Every
  field value differs across a type's 5 examples, and every boilerplate line is identical, which
  is what DocForge's analyzer needs to tell them apart (a test checks both).
- **Byte-identical builds.** python-docx writes zip entries with the current time. The generator
  therefore re-zips each file with a fixed timestamp and fixed attributes, so a rebuild on the
  same machine is byte-identical.
- **Content hash.** Compressed bytes can differ between zlib builds. A file is therefore
  identified by `content_hash`: sha256 over its parts' names and uncompressed bytes.
- **Manifest.** `manifest.json` is committed. Per document it holds the file, the content hash,
  a hash of its ground truth, and its field values. Per case it holds the file, the content hash
  and the label. The full ground truth isn't stored: `build.truth_for()` rebuilds it from the
  generator, and the truth hash proves it is the same one.
- **Corpus hash.** sha256 of the manifest's canonical JSON, without the hash field itself. It
  covers every file, every ground truth and every label.
- **Manifest check.** A test rebuilds the corpus and compares the result with the committed
  manifest; in M5, CI does the same with `git diff --exit-code`.

### 4.2 Document types

| Type | Languages | Milestone | Fields (examples) | Tables | Boilerplate worth mutating |
|---|---|---|---|---|---|
| Vendor service agreement | EN, DE | M1 | parties, reference, start date, monthly fee | fee schedule | liability cap, governing law / Gerichtsstand, notice period / Kündigungsfrist, confidentiality |
| NDA | EN, DE | M1 | parties, effective date, term | — | confidentiality obligations, term, governing law |
| Invoice | EN, DE | M1 | number, dates, customer, VAT ID / USt-IdNr., totals | line items | payment terms |
| Meeting minutes | EN | M1 | date, chair, attendees | action items | distribution note |
| Data protection impact assessment | EN | M3/M4 | purpose, data categories, legal basis | risk register | standard GDPR wording |
| Project status report | EN | M3/M4 | project, date, author, summary | tasks | confidentiality notice |

**German documents follow German conventions**
- dates like `23.11.2026`
- amounts like `1.234,56 €`
- "Gerichtsstand ist …"
- "Kündigungsfrist von drei Monaten zum Quartalsende"
- "Haftungsbeschränkung"
- "USt-IdNr."

**Per type and language**
- 5 examples: the input for analyze and for the frozen template
- 8 held-out documents: the clean controls, and the bases for mutations
- 3 or more notes cases (M3)
- mutated copies of the held-out documents (§4.3), about 2 per applicable mutator

**Case budget** (as built in M1)
- 7 type/language pairs, 91 documents, and 238 comply cases, 56 of them clean controls (24%).
- Each applicable mutator is applied to 2 held-out bases, rotating through `held_01`–`held_08`.
- Generate (M3) and analyze (M4) add about 60 cases, which keeps the total near the brief's
  150–300.

**Deferred to M4.** Key-value tables ("label | value" rows, as in a document-control block). When
their values vary, DocForge may treat such a table as a repeating table. Leaving them out of M1
keeps the comply ground truth clean, and M4 tests that behaviour on purpose.

### 4.3 Mutators

Each mutator takes a clean .docx (bytes) and its ground truth, and returns
`(mutated_bytes, label)`:

```yaml
case: service_agreement_de/held_01/change_liability_cap
mutator: change_liability_cap
targets: [clause.liability]
expected_kind: changed_fixed
material: true
rule_dependent: false
fixable: true
detail:
  before: "Außer bei Vorsatz und grober Fahrlässigkeit ist die Haftung … auf 250.000 € je Vertragsjahr beschränkt."
  after:  "Außer bei Vorsatz und grober Fahrlässigkeit ist die Haftung … auf 25.000 € je Vertragsjahr beschränkt."
```

| Mutator | Expected kind | Material | Applies to | Note |
|---|---|---|---|---|
| Change liability cap amount | `changed_fixed` | yes | agreements | A small edit in a long clause (H1) |
| Change governing law / Gerichtsstand | `changed_fixed` | yes | agreements, NDA | H1 |
| Change notice period / NDA term | `changed_fixed` | yes | agreements, NDA | H1 |
| Change payment terms (30 → 90 days) | `changed_fixed` | yes | invoices | H1. Added in M1. |
| Delete a clause (heading + body) | `missing_fixed` | from the spec (confidentiality: yes; the minutes' distribution note: no) | all | Fixable |
| Fix a typo in boilerplate | `changed_fixed` or nothing | no | all | The spec plants one consistent typo per type, and the mutator corrects it |
| Double space / punctuation / curly quotes | `changed_fixed` or nothing | no | all | |
| Change heading capitalisation (to all caps) | `changed_fixed` | no | all | H2: likely reported |
| Empty a required field | `missing_field` | yes | all | |
| Invalid value in a typed field ("TBD", "offen") | `format` | yes | types with dates | Added in M1. A date-format change raises nothing, because dates are validated with `dateutil`, so this mutator is what covers `format`. |
| Change date format (`23.11.2026` → `2026-11-23`) | `format` or nothing | no, `rule_dependent` | types with dates | Depends on the validation rules the analyzer derived |
| Remove a table row | `table_shape` (only when the last row goes) or nothing | per table spec (an invoice line is material) | invoice, minutes, agreement | H3 |
| Remove a table column | `table_shape` | yes | tables | H4: may go unreported, or come out as `missing_table` |
| Delete a whole table | `missing_table` | yes | tables | |
| Reorder two sections | nothing | no | agreements, NDA | Any report counts as a false alarm (H5) |
| Insert a benign paragraph (a note) | nothing (only an `extra` row) | no | all | |
| Insert a material paragraph ("liability is unlimited") | nothing (only an `extra` row) | yes | agreements, NDA | H6 |
| No change (clean control) | — | — | all | ≥ 20% of comply cases |

**Notes on the table**
- **"Or nothing"** marks benign changes. For those, the question is whether the change raises an
  alarm, not whether it is found.
- **Tests.** Every mutator has a unit test. It applies the mutator to a small document, then
  compares the walks before and after: exactly the intended element changed, and nothing else.
- **As built in M1.** All 17 mutators exist (the 2 inserts count separately). Their parameters
  (which clause, which words) live in each document-type spec, so a mutator applies only where
  the spec defines it.

### 4.4 Notes for generate (M3)

- At least 3 per type, in varied styles:
  - bullet points
  - an email
  - German and English mixed
  - missing information
  - a contradiction with an explicit correction, so the right answer is defined
- Format: `notes/<type>/<case>.yaml` with `text:` and `expected:`, keyed by logical field ID
  (§3.5). Written by hand and committed.

### 4.5 Hand-made set

- **Files.** `handmade/<name>.docx` plus `handmade/<name>.labels.yaml`. The labels file holds:
  - the document type
  - which corpus template the document is checked against
  - its deviations, each anchored by a short quote of the affected text, since hand-made files
    have no generator locators
- **Anchor resolution.** The runner resolves an anchor by text similarity against the
  representative's elements, and fails loudly when the match is unclear.
- **Content.** Accepted tracked changes, text pasted from an email, broken styles, a converted
  PDF. Labelled by the owner.
- **Timing.** The format is fixed in M1. The files are added when they exist.

### 4.6 Names

All people and companies are invented. Each company name gets a web search before use. The list
and the date of the check go in `corpus/NAMES.md`. No employer, client or third-party material is
used anywhere.

## 5. Metrics

- **Pure functions.** All metrics are pure functions (plain data in, numbers out) and live in
  `evals/metrics/`. Each has unit tests on tiny cases calculated by hand.
- **Counts shown.** Every rate is shown with its counts, for example `0.82 (41/50)`, so small
  samples are visible.

### 5.1 Comply

**Attribution.** In each case, a reported difference belongs to the injected deviation if it sits
on the target's node. Otherwise it's spurious. For a missing element, "the target's node" is the
template node the element came from.

| Metric | Definition |
|---|---|
| Detection recall (per kind, per mutator) | Material deviations with at least one difference on the target ÷ material deviations. An inserted paragraph counts as found only if an `alignment` row with status `extra` holds its text. |
| Kind accuracy | Found deviations whose difference has the expected kind ÷ found deviations |
| Benign alarm rate | Benign deviations reported with severity error or warning ÷ benign deviations. In AI modes this uses the severity after the judge. |
| False alarm rate (clean) | Clean controls with at least one error or warning difference ÷ clean controls, plus the mean number of such differences per clean control |
| Spurious differences | Differences not attributed to the injected deviation, per mutated case |
| Judge confusion matrix | Over the differences in cases where the judge ran, its material verdict vs. ground truth. An attributed difference takes its deviation's label; any other difference (spurious, or on a clean control) is benign. Reports precision, recall and accuracy on "material". Differences without a verdict (past the 40-item cap, or missing from the answer) are counted as "not judged". |
| Material still alarming | Found material deviations that still have an error or warning on their target after the judge ÷ found material deviations. In the no-AI run it counts found deviations that alarm. Together with the benign alarm rate, it shows what the judge changes. |
| Score separation | AUC: the chance that a random clean control scores higher than a random document with a material deviation (ties count half). Computed on `score` in every mode and on the semantic score in AI modes. A case without differences has semantic score 100: the judge isn't called and has nothing to object to. A case where the judge failed has no semantic score and is left out. Comes with a grade table: pass / warning / fail × clean / material / benign. |
| Fix success | On material cases whose deviation is a changed or missing FIXED paragraph: run `fix_document`, then check the result again. It succeeds when three things hold. (1) The re-check shows no `changed_fixed` or `missing_fixed` on the target. (2) Every field value in the alignment matches the pre-fix check. (3) The fixed document's text equals the clean original's. Part (3) is needed because a re-check uses the same 0.9 threshold as the check, so it can't see what the check missed. Restored paragraph styles are reported separately. The fixer uses no AI, so it runs in the no-AI run only, and AI runs show "n/a". |

### 5.2 Generate

**Field outcome.** Each template field that maps to a logical field with an expected entry gets
exactly one outcome, tested in this order:

| Outcome | When |
|---|---|
| correct | The value matches the expected value, or an `accept` value, after normalisation |
| correctly empty | The expected value is `null` and the output is empty |
| omitted | The expected value is not `null` and the output is empty |
| grounded but wrong | The value is wrong but appears in the notes: the wrong field, or the wrong one of two dates |
| unsupported | The value is wrong and appears nowhere in the notes. **This is a hallucination.** |

"Appears in the notes" means the normalised value is a substring of the normalised notes. Dates
and amounts also count when they equal one parsed from the notes.

| Metric | Definition |
|---|---|
| Field accuracy | correct ÷ fields whose expected value is not `null` (short fields) |
| Omission rate | omitted ÷ fields whose expected value is not `null` |
| **Hallucination rate** | unsupported ÷ fields with a non-empty output. Split into **flagged** (the placement has `ai_drafted`, so the product marked it for review) and **silent**. |
| Table row accuracy | Rows: right count, yes or no. Cells: correct ÷ expected cells. |
| Form kept | Correct values that also keep the template's written form, such as German dates and amounts |
| Layout preserved | The output has the template's blocks in the same order, with the same styles and table shapes. Repeated table rows and repeated blocks are collapsed before comparing. |
| Free-text fields | Rubric grader (§6.5): faithful (no unsupported claims) and complete (covers the expected points) |

Each case also records which engine wrote it (`writer`, `llm` or `heuristic`), whether the review
ran, and whether it led to a rewrite.

### 5.3 Analyze

Each type is run with k = 1, 2, 3 and 5 examples, using the first k of its five examples, in the
same order every run.

| Metric | Definition |
|---|---|
| Field precision / recall / F1 | Over the representative's top-level elements and key-value table cells. Predicted field: the classification needs a field (dynamic or repeatable). True field: ground-truth kind `field`. Cells of repeating tables are left out here; table detection measures them. |
| Boilerplate preservation | Ground-truth `fixed` elements classified `FIXED` ÷ ground-truth `fixed` elements |
| Field type accuracy | Among true fields that were found, how often `FieldDefinition.field_type` matches the ground truth under this map: text → text; multiline_text → multiline_text or text; date → date; person → person; number → number; money → number (open question); enum → enum |
| Repeating table detection | Ground-truth repeating tables classified `REPEATABLE_TABLE`, with columns equal to the ground-truth header row |
| Layout fidelity | `template.docx` keeps the representative's skeleton: the same blocks in the same order, the same styles and table shapes, and fixed text unchanged. Fields carry tags. The idea follows `backend/tests/unit/test_template_keeps_its_layout.py`. |

`auto` elements, such as page-number fields, are left out of precision and recall. Whether they
come out as `AUTO_FIELD` is reported on its own.

### 5.4 Measured on every run

| Metric | Definition |
|---|---|
| Cost per document (USD) | The service's own `token_usage.cost_usd`, priced from DocForge's table in `ai/pricing.py`. Per analysis, per generated document, per compliance check. |
| Live vs. replayed spend | Live: calls that went to the network in this run. Replayed: the recorded cost of cached responses. Both come from the observer (§6.4). |
| Latency p50 / p95 per step | Wall-clock time per service call. A step served from the cache reports the latency recorded when it ran live (§6.2). |
| Pipeline fallback rate | Results the deterministic engine produced even though AI was configured. **Analyze:** `source == "heuristic_fallback"`. **Generate:** `source == "heuristic"`, with `"llm"` (the writer failed or was skipped) reported separately. **Comply:** differences present but no `semantic` dimension, ÷ cases where the judge was asked. |
| AI call failure rate | From the observer: AI calls that raised `LLMError` ÷ AI calls, per call kind (understanding, classify, critique, describe, writer, route, compose, review, judge). This catches the silent ones. |
| Error rate | Cases where a service raised, or where the ground truth failed to resolve |
| Stability | `--repeat 3 --sample 10`: 10 judged cases, picked by a hash of their IDs, are checked twice more, each repeat under its own cache key. Comply reports verdict agreement (differences whose material verdict is the same in every run ÷ differences judged in every run) and the mean spread (max − min) of the semantic score. |

### 6.2 Response cache (`evals/cache.py`)

- **Where it sits.** At the HTTP transport. The eval process wraps `handle_request` in memory on
  two transports, one per AI path:
  - `httpx2.HTTPTransport`: the Anthropic SDK (1.17.0) used by `ai/anthropic_transport.py` is
    built on `httpx2`, a separate package (§1.2 #15)
  - `httpx.HTTPTransport`: the OpenAI-compatible path in `ai/client.py`, which LM Studio uses

  On a replayed response, DocForge's own request building, parsing, retries and fallbacks run
  unchanged, and `record_usage` sees the original token counts. Two contract tests replay
  recorded responses through the real `LLMClient` and `judge_compliance`: a streamed (SSE) answer
  through the real Anthropic SDK, and a JSON completion through the OpenAI-compatible path. They
  check the parsed verdicts, the recorded usage and what the observer captured. Without any
  network access, they show that both paths really go through the wrapped transports.
- **Key.** sha256 over:
  - config name, case ID and repeat index
  - HTTP method and URL path
  - the request body as canonical JSON (sorted keys), with 32-hex IDs replaced by a placeholder

  DocForge's IDs are `uuid4().hex`. Today's prompts contain none, so the masking is insurance.
- **Entry.** Status, three response headers (content type, `retry-after`, `x-should-retry`), the
  gzipped body, live latency, model and date. One file per key under `evals/cache/<config>/`.
  Entries are written atomically (temp file, then rename), because analysis makes parallel calls.
- **Only successes are stored.** A 2xx answer is stored, even when DocForge then fails to parse
  it, so a model's malformed answer replays as the same failure. An HTTP error or a timeout is
  not stored, so a rerun tries that call again. Reruns are for interrupted runs only (README).
- **Streaming.** On a live call, the wrapper reads the whole response before returning it, so
  streamed answers are cached whole. DocForge's progress callbacks then fire in one burst, which
  is harmless in a batch run.
- **Modes.**
  - Default: replay hits; on a miss, call live and record.
  - `--no-cache`: always call live, and overwrite.

  Each run records its hit rate. A code change that alters a prompt simply misses.
- **Secrets.** Request headers are not part of the key and are never stored, so neither
  `x-api-key` nor `authorization` reaches the cache.

### 6.3 Budget guard

1. **The cap.** `--max-usd` (default 3.00), and a config's `max_usd`: the stricter of the two
   wins, so a command can lower a config's cap but never raise it. `haiku.yaml` sets $1.00, the
   owner's €1 cap. For anything above $3, the owner decides first (brief §9).
2. **Before the run.**
   - Judged cases: the cases whose deterministic check has differences, read from the latest
     no-AI result. Only those reach the judge, and they're the same in every mode.
   - Estimate = (judged cases not already complete in the cache + the `--repeat` calls) × cost per
     judged case. Repeat calls are counted as uncached, so the estimate is an upper bound.
   - Cost per judged case comes from the latest result for the same config and suite. Without
     one, the first 3 judged cases are a pilot. After them, the run stops if their mean cost
     times all judged calls would pass the cap.
   - `--dry-run` checks the setup (key present, model reachable and loaded, corpus), prints the
     plan and the estimate, and calls no model.
   - If the estimate is above the cap, the run doesn't start.
3. **During the run.**
   - Live spend is updated after every case.
   - The run stops after the case whose live spend reaches the cap.
   - It then writes a partial result marked `"stopped": "budget"` (or `"budget_projection"` after
     the pilot), and says so.
4. **At the end.** Live spend and replayed cost are printed and stored.
5. **Local models.** DocForge's price table has no price for them, so they cost $0, shown as
   `$0 (hardware)`, and aren't capped.

The estimate exists to avoid starting runs that clearly can't fit. Step 3 is the real limit.

### 6.4 Call observer (`evals/observe.py`)

In-memory wrappers installed by the harness. Each calls the original and only records: arguments
and results are never changed, and no source file is edited.

- **`LLMClient.complete_agentic`, `complete_json` and `complete`** (`ai/client.py`):
  - **What it records.** `{case, call kind (from the schema class), tier, model, outcome (ok or
    LLMError), elapsed}`.
  - **Only the outermost call.** `complete_agentic` can fall back to `complete_json` internally,
    so a depth counter keeps it at one record per logical call.
  - **Judge verdicts.** When the schema is `LLMComplianceJudgement`, the returned verdicts are
    kept for the case. `verdicts[i].index` points into `report.differences`, and the judge sees
    the first 40 in order.
- **`Usage.add`** (`ai/usage.py`): prices each call with DocForge's own `cost_for_call`, and adds
  it to the run's live or replayed total. A per-call flag set by the cache tells the two apart.

### 6.5 Rubric grader (M3)

- **When it's used.** Only for free-text fields, where exact match can't work: summaries and
  descriptions. It scores two things against the notes and the expected points: faithful (no
  unsupported claims) and complete.
- **Which model.** Claude Haiku 5.5, the only cloud model in scope, set by the config's
  `grader:` block.
  - For local runs, it is a different model from the one under test, as the brief asks.
  - For Haiku runs, it grades its own model's output, which the brief warns against. The
    agreement gate below therefore decides whether its grades are used at all.
  - The grader's own cost is reported apart from the mode's cost.
- **Agreement gate.**
  - The owner hand-labels 30 items. Agreement with those labels is reported.
  - Below 85%, the grader is not used, and a sample goes to manual review instead (brief §6.4).

### 6.6 Where the AI runs happen (M2)

**Both AI runs happen on the owner's PC, with the commands in the README.**
- **No Anthropic key in the cloud container.** The cloud environment's network secrets are never
  added to requests to `api.anthropic.com`. A key would have to sit in an environment variable of
  the owner's default environment, readable by commands in every cloud session. The owner chose
  to run Haiku at home instead, with a €1 cap.
- **No LM Studio in the cloud container.** Remote Control offers no folder on the owner's PC that
  a cloud session can use, so the container can't reach LM Studio either.
- **Everything else is built and tested in the container.** The tests run without network access:
  fake model servers, recorded responses, and an end-to-end run of the CLI against a fake LM
  Studio.

**The key.** The README has the owner type the key into `Read-Host -AsSecureString`, so it
appears on no screen and in no history file, and lives only in that PowerShell window. The
harness reads it from `ANTHROPIC_API_KEY`, and it never reaches a result, the cache or a log.

**The workload, measured offline.** The full comply run, against a fake model server, shows the
judge's work:
- 82 judge calls (one per judged case), plus 20 with `--repeat 3 --sample 10`
- prompts of about 1,900 characters, plus a 900-character JSON schema: about a thousand tokens
- at most 3 differences per call

At DocForge's Haiku 5.5 prices ($0.10 / $0.50 per million input / output tokens for prompts up
to 100K tokens), which match Anthropic's list price, a few hundred output tokens per call cost a
few cents for the run. Even if all 102 calls used the full 16,000 output tokens DocForge allows
(§1.2 #18), the run would cost about $0.83, under the $1.00 cap. Costs in results are
DocForge's own estimates from `ai/pricing.py`, not the Anthropic invoice.

**Same code, clean tree.** A result records the git SHA and whether the code had uncommitted
changes. Result files don't count as changes, so the second run of the evening is still "clean"
before the first one's result is committed.

## 7. Results, report, compare

**Result files.** `evals/results/<date>_<config>_<suite>.json`, committed:

```json
{
  "meta": {
    "suite": "comply", "config": "no-ai", "models": {},
    "date": "YYYY-MM-DD", "git_sha": "...", "docforge_version": "0.21.0",
    "corpus_hash": "...", "cases": 0, "cache_hit_rate": null,
    "spend_usd": {"live": 0.0, "replayed": 0.0}, "stopped": null
  },
  "aggregates": {"...": "metric -> {value, num, den}"},
  "cases": [{"id": "...", "outcome": "...", "differences": [], "timings_ms": {}, "token_usage": null}]
}
```

- **Contents.** Only synthetic content goes into result files, so committing them is safe. Keys
  never appear.
- **`report`.** Rebuilds `RESULTS.md` from the newest result per (config, suite). Every number in
  the table links back to the file it came from. Nobody edits `RESULTS.md` by hand.
- **`compare A B [C ...]`** (built in M2). First it says whether every result used the same
  corpus, and which ones rebuilt the files locally with other library versions. Then it prints
  one column per result for the main comply metrics (`--markdown` for docs): a metric a mode
  doesn't measure shows "n/a", and a local model's cost shows "$0 (hardware)". Last, for each
  result after the first, it lists the cases whose alarm status changed, as clean / material /
  benign × alarm added / removed. That is what the judge changed. Generate and analyze flips
  (correct → hallucinated, and so on) come with those suites.
- **AI runs also record** the model, host and efforts, `temperature_sent`, the budget plan, live
  and replayed spend, the cache hit rate, `stopped`, and per case the judge's verdicts, its calls
  and their outcomes, and the tokens used.

## 8. CI

`.github/workflows/evals.yml` is added in M5, on `evals`. It runs on PRs into `evals`, and on
PRs into master only if the owner opens one.

**On every PR**
1. Set up Python 3.12.
2. Install: `pip install -e backend` and `pip install -r evals/requirements.txt`.
3. Run `python -m evals corpus build`, then `git diff --exit-code evals/corpus/manifest.json`.
4. Run `python -m pytest tests/evals -q`.
5. Run `python -m evals run --suite all --config configs/no-ai.yaml`.
6. Check the result against `evals/thresholds.yaml`. Thresholds ratchet at the current baseline:
   the no-AI path is deterministic, so a lost detection, or any other drop, fails the PR. An
   improvement raises the threshold in the same PR.

**`workflow_dispatch`.** Inputs: a config and a required `max_usd`. The workflow uses the
`ANTHROPIC_API_KEY` repository secret, and uploads the result file as an artifact for the owner to
commit.
